# 検索の質の改善（本文、順位、言語、版、節、リンク、クリック、鮮度）

ベクトル検索（[vector-search.md](vector-search.md)）を入れた後、実際の索引（開発者向けの文書、英語と日本語、約 5.8 万頁）で
質問ごとに正解の頁が何位に来るかを測り、見つかった問題を順に直した。どれも検索のたびのモデルの実行を増やさない
（重い処理は crawl のときか、後ろで少しずつ）。他のピアからの要求には、ベクトル・クリックを使わない。

## 測り方

- 索引: `docs-peer`（yacy-example）。Python、PostgreSQL、Kubernetes、Rust、MDN、Docker、Node.js、Go、Django、Pro Git
  の英語版と日本語版。
- 質問: `docs-peer/queries.json` の 67 問。調整に使った 30 問（tune）と、調整には使わず確かめるだけの 37 問
  （heldout）。キーワード（「asyncio gather」）と自然文（「run a shell command from python and capture its output」）、
  英語と日本語。正解は、その質問に答える頁（英語版と日本語版のどちらでもよい）。
- 指標: 正解の最初の順位から MRR@10（1 位で 1、2 位で 0.5、10 位より下は 0）、1 位の数、10 位以内の数。
- `docs-peer/eval.mjs`（`--compare` で 2 回の結果を質問ごとに比べる）、`yacy-example/tools/eval.sh`、`tools/sweep.sh`。

## 結果

MRR@10（調整用 tune 30 問 / 確認用 heldout 37 問）。設定は tune だけで選び、heldout で確かめた。

**同じ索引（新しい索引、約 5.8 万頁）で、一つずつ変えたとき**

| | tune | heldout | heldout キーワード | heldout 自然文 | 日本語の質問 | 10 位以内（67 問） |
|---|---|---|---|---|---|---|
| キーワードだけ、本文の連続一致の加点 10（upstream） | 0.533 | 0.562 | 0.827 | 0.250 | 0.437 | 45 |
| キーワードだけ、加点 2 | 0.562 | 0.566 | 0.834 | 0.250 | 0.437 | 46 |
| ハイブリッド（score、重み 1.0、加点 2） | **0.643** | **0.626** | 0.829 | **0.386** | **0.630** | **54** |

- ハイブリッドは、自然文の質問（「run a shell command from python and capture its output」）と日本語の質問で効く。
  キーワードの質問はほぼ変わらない（heldout 0.834 → 0.829）。検索のたびの追加は、質問 1 つの埋め込み（小さな
  モデル）と knn の問い合わせ 1 回。
- 合わせ方の比較（tune）: score 0.668、abs 0.648、rrf 0.629。重み 0.5 は 0.631、2.0 は 0.675 だが heldout で下がる
  （0.604）ので 1.0。節の埋め込みは 0.668 / 0.667（使う / 使わない）で、使わない方が速い。
- 版の集約と入ってくるリンクの文は、この指標（最初の正解の順位）を変えなかった。版の集約は 2 位以下の重なりを
  減らすためのもの。
- 言語を選んだとき（`lr`、質問の言語）: 結果のうち質問の言語の頁は、キーワードだけで英語 86% → 94%、
  ハイブリッドで英語 84% → 89%（日本語の質問は 81〜99% のまま）。MRR はほぼ同じ（ハイブリッド tune 0.643 → 0.609、
  heldout 0.626 → 0.644）。英語の質問の正解が日本語版だけ上位にあった場合は下がる。
- 同じ設定で 2 回測ると同じ値になる（並べ方を直す前は ±0.03 揺れていた）。

**並べ方の不具合（1.）を直したとき**（古い索引、約 4.9 万頁、キーワードだけ）: 直す前は測るたびに 0.55〜0.56 で
揺れ、直した後は 0.611（heldout のキーワード 0.69 → 0.88）。古い索引は Python、Kubernetes、MDN の英語版と
Rust の本が抜けていた（crawl を始めると同じホストの待ち行列が消える。`docs-peer/crawl.sh` で直した）ので、
新しい索引の値とは比べられない。

**語幹処理の副作用**: 「docker volumes」が `docker volume` の CLI の頁に、「python f-string format」が
「File Formats」の頁に当たるようになり、2 問の正解が 10 位から外れた。dataclasses、lifetimes などの複数形の
質問は当たる（キーワードだけで「rust lifetimes」1 位）。

## 直したこと

### 1. 結果の並べ方（ローカル検索）

- **届いた順に確定していた**: ローカル検索の結果は、Solr、単語の索引（RWI）、抜粋を作るスレッドから並行して届く。
  1 件目を返すときに届いていた結果から順に確定し、後から届いた点数の高い結果が前に出られなかった。条件によっては
  （`pollImmediately`）、足した直後に確定していた。同じ質問でも順位が毎回変わっていた。
  → ローカル検索では、手元の結果が全部届くまで（最大 2 秒）待ってから点数の順に並べる。P2P 検索は今まで通り。
- **単語の索引の点数の尺度が違う**: RWI の結果の点数（100 万前後）は Solr の点数（最高点で割って 100 万倍）と比べられ
  ない。Solr が下位に置いた頁を RWI の点数が上位に押し上げていた。ローカルの文書はすべて Solr にもある。
  → ローカル検索では、RWI だけが届けた結果を Solr の結果の後ろの帯に置く（RWI どうしの順序は保つ）。

### 1b. 本文の連続一致への加点

2 語以上の質問では、質問が本文に続けて現れる頁に加点する（edismax の `bq`、upstream は `text_t:"…"^10`）。この
加点は語の一致の点より大きく、「css flexbox」で、拡張の一覧の中に「CSS flexbox」と書いてあるだけの頁が、題名が
flexbox の頁より上に来ていた。`search.ranking.solr.textPhraseBoost` で設定できるようにし、既定を 2 にした
（キーワードだけの検索で調整用 0.533 → 0.562、確認用 0.562 → 0.566）。

### 2. 本文の抜き出し（crawl のとき）

- `<main>`、`<article>`、`role="main"` があれば、その中の文を本文にする（短すぎるときは使わない）。無ければ、
  `<nav>`、`<aside>`、記事の外の `<header>`/`<footer>`、`role="navigation"` など、頁の飾りの部分を除く。DocBook や
  Sphinx の飾り（`navheader`、`sphinxsidebar` などの class）も除く（`parser.html.boilerplateClasses`）。
  飾りの中のリンクは今まで通りたどる。`parser.html.mainContent=false` で元に戻る。
- 閉じ忘れたタグ（`<li>`、`<span>`）で、ある部分が頁の終わりまで続いたことにならないよう、閉じタグは中で開いた
  ままの要素も閉じる（ブラウザと同じ）。
- YaCy は句読点の無い各タグの文の後ろに「.」を足していた。`<span>` で区切られたコードは「import. asyncio. .
  sleep. (. delay.」になり、埋め込みと抜粋の雑音になっていた。「.」は段落や見出しなどのブロックの終わりだけに足す。

### 3. 言語の優先

**日本語の頁が英語と判定されていた**: YaCy の統計による判定は空白で区切った語を数えるので、コードや英語の用語を
含む日本語の頁は英語に見える。それが `.org` などの汎用の TLD（英語とみなされる）と一致すると、頁の
`<html lang="ja">` より優先されていた。索引では MDN の日本語版の 52%、Python の日本語版の 52%、Pro Git の日本語版の
48% が `en` だった。頁が日本語・中国語・韓国語を宣言していて、本文の文字の 3% 以上がその文字（かな・漢字、
漢字、ハングル）なら、宣言を使う（Python の dataclasses の頁は、コードの英字が多く日本語の文字は 8.5%）。宣言が
誤っている頁（docs.docker.jp は翻訳した頁にも `lang="en"` と書く）のため、かなが文字の 20% 以上なら日本語、
ハングルが 20% 以上なら韓国語とする。

**選んだ言語を優先する**: 検索の画面で言語を選ぶと（`lr`、保存された選択）、今までは他の言語の頁が全部消えた。既定で「優先」にした:
他の言語の頁の点数に `search.language.otherWeight`（0.5）を掛ける（Solr の boost と、ベクトルだけで入った頁の
重み）。質問に書いた `/language/ja` は今まで通り絞り込む。`search.language.mode=filter` で元に戻る。MCP の
`search_web` に `language` を足した。

### 4. 版の集約

`docs.docker.jp/v19.03/x` と `/v20.10/x`、`postgresql.org/docs/17/x` と `/docs/current/x`、末尾の `/` や `index.html`
だけ違う URL は、同じ内容で 1 ページ目を埋めていた。URL から版を表すディレクトリ（`3.12`、`v20.10`、`current` など）
を除いた形が同じ結果は、点数の高い 1 件だけ残す（`search.ranking.collapseVersions`）。ファイル名（`whatsnew/3.12.html`）
と言語は区別する。

### 5. 節の埋め込み

[vector-search.md](vector-search.md) の「節の埋め込み」。長い頁の中ほどの話題に届くはずだったが、この質問集では
正解の順位が良くならず、検索の時間が倍になったので、既定では使わない（`search.vector.sections=0`）。

### 6. 質問の処理

- Solr の本文の解析に、英語の複数形だけを戻す `EnglishMinimalStemFilter` を足した（dataclasses → dataclass、
  lifetimes → lifetime）。索引と質問の両方。再索引が必要。
- MCP の `search_web` の説明に、効く質問の書き方（固有の語、短い質問はベクトル検索のあるピアで）を書いた。

### 7. 入ってくるリンクの文

他の頁がその頁へのリンクに付けた文（「HPA」「Pod Disruption Budget」、日本語の頁からの「水平 Pod 自動スケーリング」）
は、題名に無い呼び方を持っている。`AnchorIndexer` が後ろで集めて `anchors_in_txt` に書き、キーワード検索の項目に
加えた（`search.ranking.solr.collection.boostfields` の `anchors_in_txt^2.0`）。後から crawl した頁のリンクを拾うため、
`search.ranking.anchors.refreshHours`（24）ごとに集め直す。

### 8. クリック

検索の画面で結果を開くと `api/click_p.json` に知らせ、同じ質問の次のローカル検索でその頁の点数を最大
1 + `search.ranking.clicks.weight`（0.5）倍にする（8 回で最大）。記録するのは管理者のクリックだけ（`_p`、POST）で、
公開の検索画面の訪問者が順位を動かすことはできない。`DATA/WORK/clicks.json` に保存し、他のピアには送らない。
評価の質問では測れない（クリックが無い）。

### 9. 鮮度とサイトマップ

サイトマップの取り込みは、索引の頁の自己申告の更新日とだけ比べていたので、変わっていない頁も取り直し、更新日の
無い頁で落ちていた。取得した日時より後に更新された頁と新しい頁だけを取り直すようにした。サイトマップの crawl でも
URL の絞り込み（`mustmatch`）を使えるようにした（MDN のサイトマップは全言語を含む）。絞り込みは待ち行列に入れる前に
かける（crawl の絞り込みはリンクにしかかからず、範囲外の URL が待ち行列を埋めていた）。`docs-peer/crawl.sh refresh`。

## 調べるとき

`search.debug.ranking=true` にすると、ローカル検索の各結果の点数の内訳（Solr の点数、加点、語数、最後の順位、
キーワードで見つかったか）をログに `RANKDEBUG` で書く。
